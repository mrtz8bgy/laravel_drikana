## ساختار داده

### `articles` — مقاله

| ستون | توضیح |
|------|-------|
| `id` | شناسه |
| `title` | عنوان |
| `slug` | نشانی یکتا (یکتا در سطح دیتابیس) |
| `excerpt` | خلاصه (حداکثر ۵۰۰ کاراکتر) |
| `content` | متن کامل |
| `featured_image`, `featured_image_alt` | تصویر شاخص و متن جانشین |
| `category_id` | دسته‌بندی (FK → `article_categories.id`) |
| `user_id` | کاربر ایجادکننده |
| `author_name` | نام نمایشی نویسنده (اگر با نام کاربری سامانه یکی نیست) |
| `keywords` | کلیدواژه‌ها |
| `meta_title`, `meta_description`, `canonical_url` | فیلدهای سئو |
| `status` | `draft` / `pending_review` / `published` / `archived` |
| `is_featured`, `sort_order` | نمایش ویژه و ترتیب |
| `views_count` | شمار بازدید |
| `submitted_by`, `submitted_at` | ارسال‌کننده برای بازبینی و زمان آن |
| `published_by`, `published_at` | منتشرکننده و زمان انتشار |
| `deleted_at` | حذف نرم (Soft Delete) |

### `article_categories` — دسته‌بندی موضوعی

`name` · `slug` (یکتا) · `description` · `image` · `parent_id` ·
`sort_order` · `is_active`

دسته‌بندی سلسله‌مراتبی است (`parent_id`)، پس می‌توان ساختاری مثل
«سنگ‌های قیمتی ← یاقوت» ساخت.

> دسته‌بندی‌های با عنوان فارسی نشانی خوانا نمی‌دهند. در این حالت slug به
> شکل `category-<هشت-کاراکتر-هش>` ساخته می‌شود تا یکتا بماند و در URL
> کار کند.

### `article_images` — تصاویر داخل متن

`article_id` (FK) · `path` · `original_name` · `alt` · `caption` ·
`file_size` · `mime_type` · `sort_order`

نام اصلی فایل **برای نمایش** نگه داشته می‌شود، اما فایل روی دیسک با نام
تولیدی ذخیره می‌شود (بخش «سامانه تصاویر» را ببینید).

## گردش کار وضعیت

```
   ┌─────────┐    ارسال     ┌────────────────┐   انتشار    ┌───────────┐
   │  draft  │────────────▶│ pending_review │───────────▶│ published │
   │ پیش‌نویس │   submit     │   در بازبینی    │  publish   │ منتشرشده  │
   └────┬────┘              └───────┬────────┘            └─────┬─────┘
        ▲                           │                           │
        │        بازگرداندن به پیش‌نویس (رد بازبینی)             │
        └───────────────────────────┘                           │
                                                                │  لغو انتشار
                                                                ▼
                                                          ┌───────────┐
                                                          │ archived  │
                                                          │  بایگانی  │
                                                          └───────────┘
```

| گذار | مجوز لازم | مسیر |
|------|-----------|------|
| ساخت پیش‌نویس | `articles.create` | `POST /admin/articles` |
| ویرایش پیش‌نویس | `articles.update` | `PUT /admin/articles/{id}` |
| ارسال برای بازبینی | `articles.submit` | `POST /admin/articles/{id}/submit` |
| انتشار | `articles.publish` | `POST /admin/articles/{id}/publish` |
| لغو انتشار (بایگانی) | `articles.publish` | `POST /admin/articles/{id}/unpublish` |
| حذف | `articles.delete` | `DELETE /admin/articles/{id}` |

> **تفکیک وظایف:** نویسنده‌ای که فقط `articles.submit` دارد می‌تواند
> مقاله بنویسد اما منتشر کند نه. این عمدی است: هیچ محتوایی بدون
> بازبینی روی سایت نمی‌رود. تنها مقالات `published` در بخش عمومی دیده
> می‌شوند و `archived` از سایت خارج می‌شود بدون آنکه تاریخچه از بین برود.

> **تاریخچه:** زمان ارسال در `submitted_by` / `submitted_at` و زمان
> انتشار در `published_by` / `published_at` ثبت می‌شود؛ بنابراین
> می‌توان هم «چه کسی منتشر کرد» و هم «چه زمانی» را استخراج کرد.

## بخش عمومی

بدون نیاز به ورود:

| مسیر | کاربرد |
|------|--------|
| `/articles` | فهرست مقالات منتشرشده (صفحه‌بندی‌شده) |
| `/articles/category/{slug}` | مقالات یک دسته |
| `/articles/search?q=...` | جست‌وجو در عنوان، خلاصه و متن |
| `/articles/{slug}` | نمایش مقاله |

**نکات:**

- تنها مقالات با `status = published` و `published_at <= now()` نمایش
  داده می‌شوند. مقاله پیش‌نویس با دانستن نشانی هم دیده نمی‌شود (۴۰۴).
- ترتیب روت‌ها مهم است: `articles/search` پیش از `articles/{slug}`
  ثبت شده تا `search` به‌عنوان slug تفسیر نشود.
- شمار بازدید در هر نمایش یک واحد افزایش می‌یابد.
- مقالات حذف‌شده (Soft Delete) در بخش عمومی دیده نمی‌شوند.

## نمایش در صفحه اصلی

صفحه اصلی سایت یک بخش اختصاصی برای مقالات دارد تا محتوا به مخاطب
عمومی هم دیده شود.

### چه چیزی نشان داده می‌شود

| مورد | جزئیات |
|------|--------|
| تعداد کارت | ۳ مقاله آخر منتشرشده |
| منبع داده | `HomeController@index` → `$latestArticles` |
| کوئری | `Article::published()->with('category')->latest('published_at')->take(3)` |
| خروجی خالی | بخش به‌کل نمایش داده نمی‌شود (نه قاب خالی، نه پیام خطا) |
| دسته‌ها | قرص‌های موضوعی از `$articleCategories` (فقط دسته‌بندی‌های دارای مقاله منتشرشده) |
| صرفه‌جویی کوئری | `with('category')` — پرهیز از مسئله N+1 در ۳ کارت |

### گارد نمایش

```blade
@if(isset($latestArticles) && count($latestArticles) > 0)
    <section class="d-articles"> ... </section>
@endif
```

`isset()` عامدانه گذاشته شده است: اگر کنترلر دیگری همان ویو را بدون
متغیر مقاله رندر کند (مثلاً در آینده برای پیش‌نمایش)، صفحه بی‌خطا
بالا می‌آید.

### ساختار کارت

```

├── .d-art-grid
│   ├── .d-art-card
│   │   ├── .d-art-thumb     ← تصویر شاخص (با loading="lazy")
│   │   ├── .d-art-badge     ← دسته‌بندی
│   │   └── .d-art-body
│   │       ├── .d-art-title     ← عنوان (لینک به مقاله)
│   │       ├── .d-art-excerpt   ← خلاصه
│   │       └── .d-art-meta      ← نویسنده · تاریخ شمسی · بازدید
```

### فیلدهای فرم

| گروه | فیلدها |
|------|--------|
| محتوا | عنوان، خلاصه، متن کامل، کلیدواژه‌ها |
| تصویر | تصویر شاخص، متن جانشین تصویر شاخص، تصاویر داخل متن با توضیح |
| دسته‌بندی | دسته موضوعی، نمایش ویژه، ترتیب |
| نویسنده | نویسنده/ثبت‌کننده |
| سئو | عنوان سئو، توضیح سئو، نشانی canonical |

### قواعد ویرایش بر پایه مالکیت

`articles.view_own` و `articles.update` تنها به مقالات خودِ کاربر اجازه
می‌دهند؛ `articles.update_any` و `articles.view` (بدون `_own`) به همه.
بررسی مالکیت در خود کنترلر انجام می‌شود، نه فقط در رابط کاربری:

```php
if (! $user->hasPermissionTo('articles.update_any')
    && $article->user_id !== $user->id) {
    abort(403);
}
```

## سامانه تصاویر

### مسیر ذخیره‌سازی

```
storage/app/public/uploads/articles/2026/10/   تصویر شاخص و تصاویر داخل متن
                    └── زیرپوشه سال/ماه
```

نمایش با `php artisan storage:link`. **هیچ فایلی در `public/uploads`
یا مسیر اجرایی ذخیره نمی‌شود.** پوشه `storage` بیرون از ریشه وب است و
حتی اگر لایه اعتبارسنجی دور زده شود، فایل PHP در آن اجرا نمی‌شود.

### زنجیره اعتبارسنجی

| گام | بررسی | چرا |
|-----|-------|-----|
| ۱ | `is_uploaded_file()` و کد خطای آپلود | رد آپلود ناقص یا ساختگی |
| ۲ | **نوع واقعی MIME با `finfo`** | پسوند `.jpg` روی فایل PHP را رد می‌کند |
| ۳ | MIME در فهرست سفید `image/jpeg,image/png,image/gif,image/webp` | رد نوع‌های اجرایی |
| ۴ | اندازه ≤ ۳ مگابایت (`SecureImageUploader::MAX_SIZE`) | جلوگیری از پرکردن دیسک |
| ۵ | ابعاد ≤ ۴۰۰۰×۴۰۰۰ پیکسل | جلوگیری از تصویر بمب |
| ۶ | `getimagesize()` موفق | تأیید اینکه فایل واقعاً تصویر است |
| ۷ | `basename()` روی نام اصلی | حذف مسیرهای `../` |

> ⚠ **اعتبارسنجی پسوند کافی نیست.** فایلی با نام `x.jpg` می‌تواند در
> واقع کد PHP باشد. به همین دلیل هم MIME واقعی و هم `getimagesize()`
> بررسی می‌شوند. اعتبارسنجی `image` لاراول این دو را انجام می‌دهد و ما
> فهرست پسوندها را هم محدود کرده‌ایم.

### نام‌گذاری فایل

```php
// app/Services/Media/SecureImageUploader.php
return date('Ymd') . '_' . bin2hex(random_bytes(16)) . '.' . $extension;
```

پسوند از **MIME تأییدشده** استخراج می‌شود، نه از نام اصلی فایل؛ پس
`shell.php.jpg` واقعی‌بودن تصویر را رد می‌کند و `evil.jpg` (که در واقع
PHP است) هم رد می‌شود.

نام اصلی فایل هرگز روی دیسک استفاده نمی‌شود؛ بنابراین:

- دو فایل هم‌نام یکدیگر را بازنویسی نمی‌کنند؛
- کاراکترهای خطرناک یا چندبایتی در نام فایل نمی‌مانند؛
- نام در `original_name` نگه داشته می‌شود تا در رابط کاربری نمایش داده شود.

### دسترسی به تصاویر

| عملیات | بررسی لازم |
|--------|-----------|
| مشاهده | مقاله منتشرشده → عمومی؛ پیش‌نویس → مالک یا `articles.view` |
| بارگذاری | `articles.images.manage` **و** مالکیت مقاله |
| حذف | `articles.images.manage` **و** مالکیت مقاله |
| دسترسی مستقیم به فایل | از طریق `/storage/uploads/...` — نام فایل ۱۲۸ بیت تصادفی است و حدس‌زدنی نیست |

> **چرا بررسی مالکیت روی تصویر لازم است؟** مجوز `articles.images.manage`
> می‌گوید «می‌توانی تصویر بارگذاری کنی»، نه «می‌توانی روی هر مقاله‌ای
> تصویر بارگذاری کنی». بدون بررسی دوم، یک نویسنده می‌توانست به مقاله
> دیگری تصویر بیفزاید یا تصویرش را حذف کند.

### خروجی امن در Blade

```blade
<img src="{{ asset('storage/' . $image->path) }}"
     alt="{{ $image->alt }}">
```

نشانی با `asset()` ساخته می‌شود (نه الحاق رشته از ورودی کاربر) و متن
جانشین با `{{ }}` فرار داده می‌شود.

## امنیت محتوا

### XSS در متن مقاله

متن مقاله HTML مجاز دارد، بنابراین «پاک‌سازی» ضروری است. خط لوله:

1. اعتبارسنجی در `ArticleController::rules()` پیش از ورود به سرویس انجام
   می‌شود (`$request->validate(...)`).
2. متن پیش از ذخیره از فیلترِ سفیدِ برچسب‌ها می‌گذرد:
   `p, br, strong, b, em, i, u, s, sub, sup, h2, h3, h4, h5, h6, ul, ol, li, blockquote, pre, code, a, img, table, thead, tbody, tr, th, td, figure, figcaption, hr, span, div`.
3. صفت‌های `on*` (مثل `onerror`, `onclick`) و `style` حذف می‌شوند.
4. `javascript:`, `data:`, `vbscript:` در `href` و `src` حذف می‌شوند.
5. `<script>`, `<style>`, `<iframe>`, `<object>`, `<embed>`, `<form>`, `<svg>`, `<math>`, `<template>` و تگ‌های ورودی **همراه با محتوایشان** حذف می‌شوند.
6. برای هر تگ تنها صفت‌های فهرست‌شده مجازند؛ `href`/`src` تنها با پروتکل `http`, `https`, `mailto`, `tel` یا مسیر نسبی.
7. لینک‌های دارای `target` به‌طور خودکار `rel="noopener noreferrer"` می‌گیرند.

پیاده‌سازی: `app/Services/Content/HtmlSanitizer.php` (فراخوانی از
`ArticleService` در زمان ذخیره)

**کجا استفاده می‌شود:**

```blade
{{-- متن مقاله — تنها جای Blade که از {!! !!} استفاده می‌کند --}}
{!! $article->content !!}

{{-- همه فیلدهای دیگر {{ }} و بنابراین فرار‌داده‌شده --}}
<h1>{{ $article->title }}</h1>
<p>{{ $article->excerpt }}</p>
<meta name="description" content="{{ $article->meta_description }}">
```

> **قاعده:** `{!! !!}` تنها برای `$article->content` مجاز است — چون پیش از
> ذخیره پاک‌سازی شده است. عنوان، خلاصه، کلیدواژه، توضیح سئو و متن جانشین
> تصویر همه با `{{ }}` نمایش داده می‌شوند و هرگز خام چاپ نمی‌شوند.

### XSS در عنوان و توضیح

فیلدهای `title`, `excerpt`, `keywords`, `meta_title`, `meta_description`,
`alt`, `caption` هرگز HTML نمی‌پذیرند:

- در زمان ذخیره، با `HtmlSanitizer::cleanText()` (که `strip_tags` است)
  هر تگ حذف می‌شود.
- در خروجی، با `{{ }}` فرار داده می‌شوند (لایه دوم).
- در برچسب `<meta>` هم از `{{ }}` استفاده می‌شود؛ بنابراین امکان
  بستن صفت و تزریق برچسب جدید وجود ندارد.

### اعتبارسنجی ورودی

| فیلد | قاعده |
|------|-------|
| `title` | الزامی، ۳ تا ۱۹۱ کاراکتر، بدون تگ |
| `slug` | اختیاری، یکتا، تنها `a-z0-9-` |
| `excerpt` | اختیاری، حداکثر ۵۰۰ کاراکتر |
| `content` | اختیاری، حداکثر ۵۰۰٬۰۰۰ کاراکتر |
| `featured_image` | `file`, `max:3072` (۳ مگابایت) — نوع واقعی در `SecureImageUploader` بررسی می‌شود |
| `category_id` | `nullable|exists:article_categories,id` |
| `status` | تنها مقدارهای `Article::statuses()` |
| `canonical_url` | `nullable|url` |

نکته: `exists:` و `in:` جلوی دست‌کاری شناسه (ID tampering) را می‌گیرند.

### محافظت CSRF

همه فرم‌های پنل `@csrf` دارند و درخواست‌های تغییردهنده از
POST/PUT/PATCH/DELETE استفاده می‌کنند. حذف مقاله از طریق فرم مخفی با
`@method('DELETE')` انجام می‌شود، نه با لینک GET.

## سئو

| مورد | پیاده‌سازی |
|------|-----------|
| نشانی یکتا | `slug` با قید `UNIQUE` در دیتابیس |
| عنوان سئو | `meta_title` و در نبودش `title` |
| توضیح سئو | `meta_description` و در نبودش `excerpt` |
| کلیدواژه | `keywords` در برچسب meta |
| نشانی canonical | `canonical_url` اختیاری |
| تاریخ انتشار | `published_at` در برچسب‌های Open Graph |
| تصویر شاخص | Open Graph `og:image` با نشانی مطلق |
| نقشه سایت | مقالات منتشرشده در `sitemap.xml` |

> توجه: عنوان سئو و توضیح سئو از ورودی کاربر می‌آیند و در `<meta>` با
> `{{ }}` چاپ می‌شوند. اگر جایی از `{{ $article->meta_title }}` به
> `{!! !!}` تغییر دهید، درِ XSS باز می‌شود.

## نکات پیاده‌سازی

### اسلاگ خودکار

```
"راهنمای نگهداری طلا"  →  راهنمای-نگهداری-طلا   (اسلاگ فارسی، تمیز)
"Gold Care Guide"      →  gold-care-guide
""                     →  article-<sha1[0:8]>
```

اگر اسلاگ تکراری باشد، پسوند شماره‌دار اضافه می‌شود: `...-2`, `...-3`.

### حذف نرم و بازیابی

`articles` از `SoftDeletes` استفاده می‌کند؛ بنابراین:

- حذف مقاله داده را نابود نمی‌کند (قابل بازیابی از دیتابیس).
- فایل‌های تصویر پیوست در زمان حذف **پاک نمی‌شوند** (اگر بازیابی
  لازم شود موجودند). پاک‌سازی فایل‌های یتیم به‌عهده دستور جداگانه است.
- مقالات حذف‌شده از همه کوئری‌های بخش عمومی و پنل کنار گذاشته می‌شوند.

### عملکرد

| موضوع | تصمیم |
|-------|-------|
| فهرست عمومی | صفحه‌بندی ۱۲تایی، بدون `SELECT *` |
| مقاله + دسته + نویسنده | `with(['category', 'author'])` برای حذف N+1 |
| تصاویر | تنها برای صفحه جزئیات بارگذاری می‌شوند |
| جست‌وجو | `LIKE` روی عنوان/خلاصه/متن — برای حجم بالا به ایندکس تمام‌متن مهاجرت دهید |
| شمار بازدید | افزایش مستقیم با `increment('views_count')` بدون تراکنش سنگین |
| دسته‌بندی سطح دوم | `parent_id` با ایندکس |

### کلیدهای پیام

متن‌های رابط کاربری از فایل زبان خوانده می‌شوند
(`resources/lang/{fa,en}/articles.php`) تا چندزبانی ممکن بماند.
