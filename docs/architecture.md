## نمای کلی

دریکانا یک سامانه فروشگاهی طلا و جواهر است که سه قابلیت اصلی را در کنار
فروشگاه اینترنتی گرد هم می‌آورد:

| قابلیت | توضیح |
|--------|-------|
| **فروشگاه** | خرید و فروش محصولات، سبد خرید، پرداخت، ارسال |
| **مالکیت اشیاء قیمتی** | شناسنامه اصالت، دفتر کل مالکیت، انتقال مالکیت با گردش تأیید |
| **مقالات آموزشی** | محتوای تخصصی درباره طلا، جواهر، سنگ‌های قیمتی و نگهداری اشیاء قیمتی |

به این‌ها دو سامانه پشتیبان اضافه می‌شود:

- **دسترسی نقش‌محور پویا (RBAC)** — نقش‌ها و مجوزها از پنل مدیریت قابل تعریف‌اند.
- **گزارش حسابرسی امنیتی** — همه عملیات حساس ثبت و قابل پیگیری است.

## لایه‌های نرم‌افزار

### ۱. لایه مسیر (Routes)

مسیرها به فایل‌های موضوعی تقسیم شده‌اند. هیچ منطق تجاری در مسیرها نیست.

- نام همه مسیرها **یکتا** است (آزمون `RouteIntegrityTest` این را تضمین می‌کند).
- همه مسیرهای API نامشان با پیشوند `api.` شروع می‌شود تا با مسیرهای وب تداخل نکنند.
- هیچ عملیات تغییردهنده‌ای با متد `GET` انجام نمی‌شود.

### ۲. لایه میدل‌ور (Middleware)

زنجیره درخواست به‌ترتیب زیر است:

```
درخواست
   ↓  SecurityHeaders        افزودن سرصفحه‌های امنیتی به پاسخ
   ↓  EncryptCookies         رمزنگاری کوکی‌ها
   ↓  AuthenticateSession    ابطال نشست پس از تغییر رمز
   ↓  VerifyCsrfToken        بررسی توکن CSRF روی درخواست‌های تغییردهنده
   ↓  auth                   احراز هویت
   ↓  admin  (IsAdmin)       دروازه ورود به ناحیه مدیریت
   ↓  permission:xxx         بررسی مجوز مشخص
   ↓  Policy (در کنترلر)     بررسی مالکیت و شرایط رکورد
کنترلر
```

### ۳. لایه کنترلر (Controllers)

کنترلرها «نازک» نگه داشته شده‌اند: اعتبارسنجی ورودی، فراخوانی سرویس،
و بازگرداندن پاسخ. منطق حساس در سرویس‌ها قرار دارد.

### ۴. لایه سرویس (Services)

| سرویس | مسئولیت |
|-------|---------|
| `OwnershipTransferService` | گردش کامل انتقال مالکیت در یک تراکنش با قفل ردیف |
| `ArticleService` | چرخه انتشار مقاله و کنترل مجوز هر گذار وضعیت |
| `SecureImageUploader` | اعتبارسنجی واقعی تصویر، نام‌گذاری امن، ذخیره‌سازی کنترل‌شده |
| `HtmlSanitizer` | پاک‌سازی HTML مقالات علیه XSS |
| `AuditLogger` | ثبت رخدادهای حساس در `audit_logs` |
| `RbacService` | ساخت/ویرایش نقش و مجوز، محافظت از نقش‌های سیستمی |
| `PermissionRegistry` | فهرست مرجع مجوزها و سطح نقش‌ها |

### ۵. لایه مدل (Models)

مدل‌ها تنها ساختار داده و رابطه‌ها را توصیف می‌کنند. عملیات تجاری پیچیده
در سرویس‌ها انجام می‌شود.

## مدل داده

### موجودیت‌های اصلی

```
User (کاربر)
 ├─ role_user ──── Role (نقش)
 │                   └─ permission_role ──── Permission (مجوز)
 ├─ jewelry_owners (پرونده مالکیت)
 │      └── jewelry_certificates (شناسنامه قطعه)
 │             ├── ownership_history (دفتر کل مالکیت — فقط-افزودنی)
 │             ├── jewelry_transfers (انتقال‌ها با گردش تأیید)
 │             ├── repair_orders (سفارش تعمیر)
 │             │      └── repair_order_status_logs (تاریخچه وضعیت)
 │             └── missing_reports (گزارش مفقودی/سرقت)
 ├─ articles (نویسنده)
 │      └── article_images
 └─ audit_logs (رخدادهای امنیتی)
```

### جداول کلیدی

| جدول | نقش | نکته مهم |
|------|-----|----------|
| `roles` | نقش‌ها | جدول موجود پروژه توسعه داده شد؛ ستون `permissions` (JSON) برای سازگاری حفظ شد اما مرجع واقعی `permission_role` است |
| `permissions` | مجوزهای اتمی | ۸۶ مجوز در ۱۴ گروه |
| `role_user` | نگاشت کاربر↔نقش | یک کاربر می‌تواند چند نقش داشته باشد |
| `permission_role` | نگاشت نقش↔مجوز | مرجع نهایی مجوزها |
| `ownership_history` | دفتر کل مالکیت | ستون `sequence_no` با محدودیت یکتایی روی `(certificate_id, sequence_no)` |
| `jewelry_transfers` | انتقال مالکیت | ستون `status`: pending / approved / rejected / cancelled |
| `audit_logs` | گزارش حسابرسی | شامل `old_values`/`new_values` برای پیگیری تغییرات |
| `articles` | مقالات | `status`: draft / pending_review / published / archived |
| `article_categories` | دسته‌های موضوعی | پشتیبانی از زیردسته با `parent_id` |

### جدول‌های واسط — چرا ستون JSON کافی نبود؟

جدول `roles` از ابتدا ستون `permissions` از نوع JSON داشت. این ساختار
دو محدودیت جدی دارد:

1. **قابل پرس‌وجو نیست** — نمی‌توان با ایندکس پرسید «کدام نقش‌ها مجوز
   `articles.publish` را دارند؟».
2. **یکپارچگی ارجاعی ندارد** — امکان حذف مجوزی که در JSON باقی مانده وجود دارد.

به همین دلیل جداول `permissions` و `permission_role` ساخته شد. ستون JSON
حذف نشد (برای سازگاری با کد قدیمی و جلوگیری از شکستن نصب‌های موجود)، اما
کدی که مجوز بررسی می‌کند از آن استفاده نمی‌کند.

## لایه دسترسی

سه لایه مستقل روی هم قرار می‌گیرند (Defense in Depth):

| لایه | ابزار | چه چیزی را کنترل می‌کند |
|------|-------|--------------------------|
| ۱ | میدل‌ور `permission:` | آیا کاربر مجوز «عملیات» را دارد؟ |
| ۲ | Gate پویا (`@can`, `authorize`) | همان مجوز، برای استفاده در ویو و کنترلر |
| ۳ | Policy | آیا کاربر مجاز به این «رکورد مشخص» است؟ |

سیاست پیش‌فرض **Deny by Default** است: اگر مجوزی مشخص نشده باشد، درخواست رد می‌شود.

جزئیات کامل در [`roles-and-permissions.md`](roles-and-permissions.md).

## تصمیم‌های معماری

هر تصمیم با دلیل و گزینه‌های رد‌شده ثبت شده است تا در آینده کسی بدون
دلیل آن را برنگرداند.

### ۱. استفاده مجدد از جدول `roles` به‌جای ساخت جدول جدید

**تصمیم:** جدول `roles` موجود با افزودن ستون‌های `slug`, `description`,
`level`, `is_system`, `is_active` توسعه یافت.

**دلیل:** قانون «از ایجاد ساختار تکراری جلوگیری کن». ساخت جدول
`roles` دوم باعث دو منبع حقیقت و ناسازگاری داده می‌شد.

**گزینه رد‌شده:** ساخت جدول `rbac_roles` جداگانه — رد شد چون داده موجود
را بی‌استفاده می‌کرد.

### ۲. دفتر کل مالکیت «فقط-افزودنی»

**تصمیم:** `ownership_history` هیچ‌گاه رکورد قدیمی را بازنویسی نمی‌کند؛
هر تغییر یک رکورد جدید با `sequence_no` بعدی می‌سازد.

**دلیل:** سابقه مالکیت باید قابل استناد و غیرقابل‌دستکاری باشد. اگر
رکورد قدیمی ویرایش شود، پیگیری «چه کسی و کِی» از بین می‌رود.

**محافظ فنی:** محدودیت یکتایی روی `(certificate_id, sequence_no)`
از ثبت دو رویداد هم‌شماره در شرایط رقابتی (Race Condition) جلوگیری می‌کند.

### ۳. تغییر `owner_id` فقط در یک نقطه

**تصمیم:** ستون `jewelry_certificates.owner_id` تنها در متد
`OwnershipTransferService::approve()` تغییر می‌کند.

**دلیل:** اگر چند نقطه بتوانند مالک را عوض کنند، امکان بروز حالت
«دو مالک همزمان» یا ناهماهنگی با دفتر کل بوجود می‌آید. تمرکز در یک
نقطه، بازبینی و آزمون را ممکن می‌سازد.

### ۴. تفکیک `permission_role` به‌عنوان مرجع نهایی

**تصمیم:** بررسی مجوز از `permission_role` خوانده می‌شود، نه از ستون
JSON در `roles`.

**دلیل:** قابلیت پرس‌وجو، یکپارچگی ارجاعی، و امکان کش مؤثر.

**سازگاری:** ستون JSON هم‌زمان به‌روز نگه داشته می‌شود تا کد قدیمی نشکند.

### ۵. فیلدهای حساس با `forceFill`

**تصمیم:** فیلدهایی مثل `is_verified`, `owner_id`, `approved_by` از
`$fillable` خارج‌اند و فقط با `forceFill()` تنظیم می‌شوند.

**دلیل:** محافظت در برابر حمله Mass Assignment. کاربر نمی‌تواند با
فرستادن فیلد اضافی در فرم، مالکیت یا تأیید را جعل کند.

### ۶. سطح نقش در `PermissionRegistry`

**تصمیم:** وزن هر نقش (۱۰۰ برای مدیر کل تا ۱۰ برای کاربر عادی) در یک
فایل مرجع متمرکز است، نه پراکنده در کد.

**دلیل:** جلوگیری از اعطای دسترسی بالاتر توسط کاربر پایین‌تر. قانون:
مدیریت نقش تنها برای «مدیر کل سیستم» ممکن است و کاربر نمی‌تواند به
خودش نقش بالاتر بدهد.

### ۷. ساخته‌نشدن ستون‌های `verified_at` / `verified_by`

**تصمیم:** ستون `verification_notes` اضافه شد، اما `verified_at` و
`verified_by` ساخته نشدند و کنترلر به `approved_at` / `approved_by`
منتقل شد.

**دلیل:** این چهار ستون یک معنی داشتند. ساخت ستون تکراری باعث ابهام
«کدام مرجع است؟» و ناهماهنگی داده می‌شد.

### ۸. یک فایل CSS برای هر زمینه بارگذاری، نه یک فایل برای هر صفحه

**تصمیم:** CSS صفحاتی که در «یک صفحه با هم بارگذاری می‌شوند» جدا نگه
داشته شد (مثلاً `auth.css` و `auth-register.css`)، اما CSS صفحاتی که
هرگز با هم دیده نمی‌شوند در یک فایل ادغام شد.

**دلیل:** اگر دو صفحه با انتخابگرهای هم‌نام در یک فایل ادغام شوند،
قواعد یکی روی دیگری اثر می‌گذارد و ظاهر می‌شکند. تشخیص تداخل با یک
اسکریپت خودکار پیش از ادغام انجام شد.

### ۹. داخل‌ماندن `session_start()` در کنترلرهای پرداخت

**تصمیم:** نشست بومی PHP از `PublicSslCommerzPaymentController` حذف شد
و همه مقادیر به نشست لاراول منتقل شدند.

**دلیل:** `session_start()` در سطح فایل با هر بارگذاری خودکار کلاس اجرا
می‌شد و در خط فرمان و آزمون‌ها خطا می‌داد. مخلوط‌کردن دو سیستم نشست
هم در درایورهای غیر‌فایلی (redis/database) کار نمی‌کند.

### ۱۰. حذف «کدهای در پشتی» فروشنده، به‌جای نگه‌داشتن سازگاری

**تصمیم:** سه قطعه کد از نسخه اصلی فروشنده — `productDescCache()`،
`cartSetup()` و دو تابع مبهم‌سازی `loaded_class_select()` /
`config_key_provider()` — به‌کل حذف شدند؛ نه اینکه غیرفعال یا
«امن‌سازی‌شده» بمانند.

**دلیل:** این کدها هیچ ارتباطی با قابلیت‌های سامانه نداشتند:

| کد | کاری که می‌کرد | چرا حذف و نه اصلاح |
|----|----------------|--------------------|
| `productDescCache()` + مسیر `/config_content` | نوشتن فایل روی مسیر دلخواه، بدون احراز هویت و بدون CSRF | «امن‌سازی» یعنی افزودن احراز هویت به قابلیتی که هیچ کاربردی ندارد |
| `cartSetup()` | ارسال نشانی صفحه‌ها به یک نشانی ایمیل بیرونی | هیچ قابلیتی به آن وابسته نبود؛ کوکی همراه آن هم کاربرد دیگری نداشت |
| `loaded_class_select()` / `config_key_provider()` | پنهان‌کردن نام توابع حساس در رشته‌های عددی | تنها مصرف‌کننده‌شان دو مورد بالا بودند |

**قاعده‌ای که از این تصمیم بیرون آمد:** پیش از حذف هر چیزی، **تمام
ارجاع‌های آن در پروژه** (کنترلر، ویو، مدل، روت، پیکربندی، آزمون)
جست‌وجو می‌شود. اگر مصرف‌کننده سالمی وجود داشت، حذف انجام **نمی‌شود**؛
این قاعده درباره چهار فایلی که حذف شدند هم رعایت شد.

**نشانه‌های کد در پشتی که در بازبینی باید جدی گرفته شوند:**

- نام تابع با کارکردش هم‌خوانی ندارد (`cartSetup` که ایمیل می‌فرستد).
- رشته‌ها با الگوی عددی مبهم‌سازی شده‌اند.
- عملیات شبکه‌ای یا نوشتن فایل بدون هیچ مسیر کاربردی در سامانه.
- تابعی که فقط از یک نقطه صدا زده می‌شود و خروجی‌اش مصرف نمی‌شود.

جزئیات کامل: `docs/security-audit.md` — موارد `C-04` و `C-05`.

### ۱۱. یک فایل پیکربندی برای همه یکپارچه‌سازی‌ها

**تصمیم:** تمام کلیدهای پیامک، درگاه پرداخت، رهگیری و کدهای توسعه در
یک فایل تازه `config/drikana.php` گرد آمدند و کد برنامه از `config()`
می‌خواند، نه از `env()`.

**دلیل:** در Laravel 5.8، بوت‌استر `LoadEnvironmentVariables` هنگام
وجود کش پیکربندی از خواندن `.env` صرف‌نظر می‌کند:

```php
if ($app->configurationIsCached()) { return; }
```

پس هر `env()` در کد برنامه با `config:cache` مقدار `null` می‌دهد —
بدون خطا و بدون لاگ. با ۷۵ فراخوانی پخش‌شده در ۳۵ ویو و ۲۰ فایل کد،
`config:cache` عملاً برای این پروژه ممنوع بود.

**چرا یک فایل، نه چند فایل؟** یکپارچه‌سازی‌های اختیاری این پروژه همگی
از یک جنس‌اند («کلید سرویس بیرونی»): با `null` می‌آیند، خالی‌بودنشان
یک حالت معتبر است، و از پنل مدیریت پر می‌شوند. نگه‌داشتن‌شان در یک
فایل، جای «کجا باید اضافه شود؟» را حذف می‌کند.

**استثناها:** `env()` در `MakeSuperAdmin` (رمز بوت‌استرپ نباید داخل
کش پیکربندی به‌صورت متن روشن بنشیند) و در `InstallController` (نام
کلید پویا و اجرای پیش از نصب). هر دو در `ConfigCacheSafetyTest` با
دلیل مستند شده و آزمون، کهنه‌شدن استثنا را هم بررسی می‌کند.

## بنر اصلی صفحه اصلی (اسلایدر)

### جریان داده

```
جدول sliders  →  HomeController::publishedSliders()  →  frontend/index.blade.php
   (پنل مدیر)          (فیلتر و ترتیب)                    (بخش .fullwidth-slider-section)
```

| لایه | فایل | مسئولیت |
|------|------|---------|
| مدیریت | `admin/frontend_settings/sliders` (`SliderController`) | بارگذاری، فعال/غیرفعال، حذف |
| اعتبارسنجی | `SliderController@store` | نوع محتوا، حجم، تعداد، ابعاد |
| کوئری | `HomeController::publishedSliders()` | فقط `published = 1`، ترتیب `id`، حذف اسلاید بی‌تصویر |
| نمایش | `resources/views/frontend/index.blade.php` | مارک‌آپ بنر، گرفتن کلاس‌های CSS موجود |
| استایل | `public/css/drikana/store.css` (`.fullwidth-slider-section`) | ظاهر بنر |
| رفتار | `public/frontend/js/main.js` → `slickInit()` | راه‌اندازی `.slick-carousel` با `data-slick-*` |

### دو تصمیم طراحی

**۱) سبک‌سازی در ویو انجام می‌شود، نه در کنترلر.** ویو `@if(isset($sliders)
&& $sliders->count() > 0)` دارد؛ اگر اسلایدی نباشد، بخش به‌کل رندر نمی‌شود
و صفحه اصلی دقیقاً مثل قبل می‌ماند. این «انحطاط تدریجی» برای صفحه اصلی
حیاتی است: نبود داده نباید کادر خالی یا خطا بسازد.

**۲) اسلاید بی‌تصویر نمایش داده نمی‌شود.** کنترلر رکوردی را که فایل
تصویرش روی دیسک نیست از فهرست نمایش حذف می‌کند، اما رکورد دیتابیس را
دست نمی‌زند. دلیل: بنر شکسته اعتماد کاربر را می‌برد و مدیر باید از پنل
تصمیم بگیرد (حذف یا جای‌گزینی تصویر). نشانی‌های `http(s)://` (تصویر
روی CDN) بدون بررسی فایل پذیرفته می‌شوند.

### تاریخچه — چرا اسلایدر دیده نمی‌شد؟

پنل مدیر و CSS بنر از ابتدا وجود داشتند (`sliders` جدول،
`SliderController`، `.fullwidth-slider-section` در `store.css`)، اما
**هیچ‌جا از سایت اسلایدها رندر نمی‌شد**: در بازطراحی لوکس
(`feat: Drikana v2.0`) بخش بنر با یک «HERO استاتیک» جای‌گزین شده و
مارک‌آپ `@foreach (\App\Slider::where('published', 1)->get() ...)`
از ویو حذف شده بود. نتیجه: اسلایدهای بارگذاری‌شده در صفحه اصلی دیده
نمی‌شدند. اصلاح: بازگشت مارک‌آپ بنر **با همان کلاس‌های CSS موجود**
(بدون CSS تازه) در بالای صفحه، پیش از بخش `d-hero`.

آزمون: `tests/Feature/HomeSliderTest.php` (۹ آزمون / ۲۵ assertion) —
شامل رندر اسلایدهای منتشرشده، رد اسلاید غیرفعال، رد اسلاید بی‌تصویر،
حذف کامل بخش در نبود اسلاید، ترتیب پایدار و سخت‌سازی پیوند بیرونی.

## گسترش سامانه

### افزودن یک مجوز جدید

1. مجوز را در `app/Services/Rbac/PermissionRegistry.php` تعریف کنید.
2. `php artisan db:seed --class=RbacSeeder --force` را اجرا کنید.
3. مجوز را به نقش‌ها بدهید (از پنل `/admin/roles` یا در سیدر).
4. روی مسیر مربوطه `->middleware('permission:slug')` بگذارید.

### افزودن یک ماژول جدید

لایه‌ها را جدا نگه دارید:

```
routes/xyz.php                 مسیرها + میدل‌ور مجوز
app/Http/Controllers/Xyz/      کنترلر نازک
app/Services/Xyz/              منطق تجاری
app/Models/Xyz.php             مدل و رابطه‌ها
app/Policies/XyzPolicy.php     کنترل دسترسی در سطح رکورد
database/migrations/           ساختار داده
tests/Feature/XyzTest.php      آزمون‌ها
```
