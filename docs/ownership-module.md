# ماژول مالکیت اشیاء قیمتی

> هر قطعه طلا، جواهر یا شیء قیمتی در این سامانه یک **شناسنامه** دارد.
> همه رویدادهای مالکیت آن قطعه در یک **دفتر کل فقط-افزودنی** ثبت می‌شود
> و هیچ تغییری بدون ردپای کاربر و زمان انجام نمی‌گیرد.

## اصول طراحی

| اصل | پیاده‌سازی |
|-----|-----------|
| هر شیء شناسه یکتا دارد | `jewelry_certificates.id` + `serial_number` |
| سابقه مالکیت قابل پیگیری است | جدول `ownership_history` |
| مالک فعلی همیشه مشخص است | `jewelry_certificates.owner_id` |
| سابقه نهایی قابل حذف/بازنویسی نیست | دفتر کل فقط-افزودنی + نبود روت حذف |
| هر تغییر به کاربر و زمان نسبت داده می‌شود | `recorded_by`, `effective_at`, `audit_logs` |
| دو مالک همزمان ممکن نیست | قفل ردیف + بررسی در تراکنش |
| انتقال همزمان/تکراری ممکن نیست | قفل ردیف + بررسی وضعیت درخواست |

## مدل داده

### `jewelry_owners` — پرونده مالکیت

اطلاعات هویتی مالک (نام کامل، کد ملی، تلفن، نشانی) که می‌تواند به یک
کاربر سامانه (`user_id`) گره بخورد یا مستقل باشد (مالک حقیقی بدون حساب).

### `jewelry_certificates` — شناسنامه قطعه

| ستون | توضیح |
|------|-------|
| `id` | شناسه یکتای قطعه |
| `serial_number` | شماره سری چاپ‌شده روی شناسنامه |
| `owner_id` | **مالک فعلی** — تنها از یک نقطه تغییر می‌کند |
| `product_name`, `metal_type`, `purity`, `weight`, `stone_type` | مشخصات قطعه |
| `certificate_file`, `description` | تصویر و توضیح |
| `is_verified`, `approved_by`, `approved_at` | وضعیت تأیید اصالت |
| `rejected_at`, `rejection_reason`, `verification_notes` | وضعیت رد و یادداشت |
| `is_active` | فعال/غیرفعال بودن شناسنامه |

### `ownership_history` — دفتر کل مالکیت

| ستون | معنی |
|------|------|
| `certificate_id` | قطعه مربوطه |
| `sequence_no` | شماره ترتیبی رویداد در این قطعه |
| `from_owner_id` | مالک پیشین (برای رویداد اول: خالی) |
| `to_owner_id` | مالک جدید |
| `transfer_id` | انتقال مرتبط، در صورت وجود |
| `event_type` | نوع رویداد: `initial` / `transfer` / `correction` |
| `declared_value` | ارزش اعلام‌شده در این رویداد |
| `notes` | توضیح |
| `recorded_by` | کاربری که رویداد را ثبت کرده |
| `effective_at` | زمان مؤثر بودن رویداد |

> **محافظ کلیدی:** محدودیت `UNIQUE (certificate_id, sequence_no)`.
> این محدودیت در سطح دیتابیس تضمین می‌کند دو رویداد هم‌شماره برای یک
> قطعه ثبت نشود — حتی اگر دو درخواست دقیقاً همزمان برسند.

### `jewelry_transfers` — انتقال‌ها

| ستون | معنی |
|------|------|
| `certificate_id` | قطعه |
| `from_owner_id` / `to_owner_id` | مبدأ و مقصد |
| `status` | `pending` / `approved` / `rejected` / `cancelled` |
| `transfer_type` | نوع انتقال (فروش، هبه، ارث، ...) |
| `price` | مبلغ معامله |
| `contract_file` | سند/قرارداد پیوست |
| `requested_by` | کاربر درخواست‌دهنده |
| `approved_by`, `approved_at`, `approval_note` | تأییدکننده، زمان و یادداشت |
| `transfer_date`, `notes` | تاریخ انتقال و توضیحات |

### `repair_orders` — سفارش تعمیر

تنها تعمیرکاران مجاز با مجوز `jewelry.repairs.*` به آن دسترسی دارند.
تاریخچه تغییر وضعیت در `repair_order_status_logs` ثبت می‌شود.

### `missing_reports` — گزارش مفقودی/سرقت

| ستون | معنی |
|------|------|
| `jewelry_id` | شناسه شناسنامه (`jewelry_certificates.id`) |
| `type` | مفقودی یا سرقت |
| `location`, `description` | محل و شرح |
| `police_report_path`, `police_report_name` | فایل گزارش پلیس |
| `status` | وضعیت پیگیری |

## گردش کار انتقال مالکیت

```
                    ┌──────────────────┐
                    │  ثبت درخواست     │   مالک فعلی یا مدیر مالکیت
                    │  status=pending  │   مجوز: jewelry.transfers.create
                    └────────┬─────────┘
                             │
             ┌───────────────┼───────────────┐
             ▼               ▼               ▼
      ┌────────────┐  ┌────────────┐  ┌────────────┐
      │  تأیید     │  │  رد        │  │  لغو       │
      │ approved   │  │ rejected   │  │ cancelled  │
      └──────┬─────┘  └────────────┘  └────────────┘
             │         مجوز: approve/reject    مجوز: cancel
             │         دلیل اجباری              تنها درخواست‌دهنده
             ▼
   ┌─────────────────────────────────────────────┐
   │ نهایی‌سازی (در یک تراکنش با قفل ردیف)        │
   │  ۱. قفل ردیف شناسنامه                        │
   │  ۲. بررسی مجدد مالک فعلی == from_owner       │
   │  ۳. بررسی status == approved                 │
   │  ۴. بررسی active نبودن انتقال دیگر برای قطعه │
   │  ۵. تغییر owner_id                           │
   │  ۶. ثبت ردیف جدید در ownership_history        │
   │  ۷. ثبت در audit_logs                        │
   └─────────────────────────────────────────────┘
```

### سه لایه اعمال مجوز

| لایه | جای بررسی | چه چیزی را می‌سنجد |
|------|-----------|-------------------|
| ۱. میدل‌ور مسیر | `routes/web.php` | مجوز اتمی (`jewelry.transfers.view/create/approve/reject/cancel`) |
| ۲. Policy | `Policies/OwnershipTransferPolicy.php` | مالکیت رکورد — آیا این کاربر روی **این** انتقال حق اقدام دارد |
| ۳. سرویس | `OwnershipTransferService` | وضعیت رکورد و قواعد گردش‌کار (مثلاً لغو فقط توسط درخواست‌دهنده) |

> **Deny by Default:** اگر هیچ‌کدام از سه لایه اجازه ندهد، درخواست رد
> می‌شود. مسیر بدون میدل‌ور، ویو بدون بررسی و کنترلر بدون Policy —
> هیچ‌کدام فرض «مجاز» نمی‌گیرند.

### گام‌به‌گام

**۱. ثبت درخواست**

```php
$transfer = app(OwnershipTransferService::class)->requestTransfer([
    'certificate_id' => $certificate->id,
    'to_owner_id'    => $newOwner->id,
    'transfer_type'  => 'فروش',
    'price'          => 12500000,
    'transfer_date'  => '1404/07/20',
    'notes'          => 'توضیح درخواست',
    'contact_info'   => 'اطلاعات تماس با مالک جدید',
], $requestingUser);
```

بررسی‌های انجام‌شده:
- مجوز `jewelry.transfers.create` (روی میدل‌ور مسیر)
- کاربر درخواست‌دهنده مالک فعلی قطعه است (یا مجوز مدیریتی دارد)
- مالک مقصد ≠ مالک مبدأ
- انتقال «در جریان» دیگری برای این قطعه وجود ندارد

**۲. تأیید**

```php
$service->approve($transfer->id, $approvingUser, 'یادداشت تأیید');
```

بررسی‌ها:
- مجوز `jewelry.transfers.approve`
- Gate `ownership.transfer.approve-distinct` → تأییدکننده ≠ درخواست‌دهنده
- وضعیت فعلی `pending` است

**۳. رد**

```php
$service->reject($transfer->id, $approvingUser, 'دلیل رد — اجباری');
```

دلیل رد **الزامی** است و در `approval_note` و `audit_logs` ثبت می‌شود.

**۴. لغو**

```php
$service->cancel($transfer, $user);
```

تنها درخواست‌دهنده (یا مدیر کل) می‌تواند لغو کند و فقط در حالت `pending`.

## محافظت‌های همزمانی

| خطر | محافظ |
|-----|-------|
| دو مالک همزمان برای یک قطعه | `jewelry_certificates.owner_id` تنها در یک متد و داخل تراکنش با `lockForUpdate()` تغییر می‌کند |
| دو انتقال همزمان روی یک قطعه | پیش از نهایی‌سازی، وجود انتقال «در جریان» دیگر بررسی می‌شود |
| دو رکورد هم‌شماره در دفتر کل | محدودیت `UNIQUE (certificate_id, sequence_no)` در سطح دیتابیس |
| درخواست تکراری (دوبار کلیک) | بررسی وجود انتقال در جریان پیش از ثبت |
| تغییر مالک در فاصله درخواست تا تأیید | در لحظه نهایی‌سازی، مالک فعلی **دوباره** خوانده و با `from_owner_id` مقایسه می‌شود |

### چرا «بررسی دوباره» حیاتی است؟

فرض کنید مدیر مشغول تأیید درخواستی است. در همین فاصله، از مسیر دیگری
قطعه به شخص سومی منتقل می‌شود. اگر سرویس هنگام تأیید تنها به وضعیت
درخواست نگاه کند و مالک فعلی را بازخوانی نکند، نتیجه‌اش این است که
انتقالی از «مالکی که دیگر مالک نیست» انجام می‌شود و دفتر کل با واقعیت
ناهماهنگ می‌گردد. به همین دلیل، بررسی مالک فعلی **داخل همان تراکنش و
پس از قفل ردیف** انجام می‌شود.

## بازیابی سابقه مالکیت تاریخی

قطعاتی که **پیش از** راه‌اندازی دفتر کل ثبت شده بودند، رکورد مالکیت
اولیه ندارند. برای ساخت آن‌ها از دستور زیر استفاده کنید:

```bash
# نخست به‌صورت آزمایشی — هیچ تغییری در دیتابیس نمی‌دهد
php artisan drikana:backfill-ownership-history --dry-run

# اجرای واقعی
php artisan drikana:backfill-ownership-history

# برای دیتابیس‌های بزرگ، اندازه دسته را کنترل کنید
php artisan drikana:backfill-ownership-history --chunk=200
```

دستور برای هر شناسنامه‌ای که رکورد مالکیت ندارد، یک ردیف با
`sequence_no = 1` و `event_type = 'initial'` می‌سازد. شناسنامه‌های دارای
رکورد دست‌نخورده می‌مانند، بنابراین اجرای دوباره دستور بی‌خطر است.

> **قطعات تازه از این دستور بی‌نیازند.** یک
> `JewelryCertificateObserver` هنگام ساخت شناسنامه، رکورد مالکیت اولیه
> را خودکار ثبت می‌کند.

## گزارش‌گیری و جست‌وجو

### گزارش‌های مدیریتی (سراسری)

| گزارش | مسیر | معیارها |
|-------|------|---------|
| جامع | `/admin/jewelry/reports` | آمار کلی، توزیع فلز، روند ماهانه |
| شناسنامه‌ها | `/admin/jewelry/reports/certificates` | بازه تاریخ، نوع فلز |
| تعمیرات | `/admin/jewelry/reports/repairs` | بازه تاریخ، وضعیت، تکنسین |
| انتقالات | `/admin/jewelry/reports/transfers` | بازه تاریخ، وضعیت، نوع انتقال |
| آمار زنده | `/admin/jewelry/reports/live-stats` | شمارش لحظه‌ای برای داشبورد |
| نمودارها | `/admin/jewelry/reports/charts` | داده سری‌های زمانی (JSON) |
| خروجی CSV | `/admin/jewelry/reports/export` | همان فیلترها، خروجی قابل دانلود |

> این گزارش‌ها سراسری‌اند و به `Jewelry\Admin\ReportController` متصل
> هستند. کنترلر گزارش مالک‌محور (`Jewelry\ReportController`) حذف نشده و
> در پنل کاربری باقی است.

### گزارش‌های مالک‌محور (پنل کاربری)

| گزارش | مسیر | دامنه داده |
|-------|------|-----------|
| شناسنامه‌های من | `/my-jewelry/reports/certificates` | فقط قطعات مالکیت کاربر |
| تعمیرات من | `/my-jewelry/reports/repairs` | فقط سفارش‌های کاربر |
| انتقالات من | `/my-jewelry/reports/transfers` | فقط انتقال‌های مرتبط با کاربر |
| مالی من | `/my-jewelry/reports/financial` | بازه تاریخ، ارزش قطعات کاربر |
| خروجی | `/my-jewelry/reports/export` | خروجی CSV داده‌های خود کاربر |

> محدودسازی این گزارش‌ها در خود کنترلر با `Auth::id()` انجام می‌شود؛
> یعنی حتی با دست‌کاری پارامترهای درخواست، داده کاربر دیگری برنمی‌گردد.

**جست‌وجوی قطعه** از سه راه ممکن است:

1. شماره سریال شناسنامه (`serial_number`)
2. شناسه قطعه (`id`)
3. اطلاعات مالک مجاز (نام، کد ملی، تلفن)

**استعلام عمومی اصالت** در `/jewelry/certificate-verify` برای هر فردی
قابل استفاده است و اطلاعات هویتی مالک را نشان نمی‌دهد.

## گزارش حسابرسی

هر عملیات حساس روی مالکیت در `audit_logs` ثبت می‌شود:

| رخداد | کِی ثبت می‌شود |
|-------|----------------|
| `ownership.transfer.requested` | ثبت درخواست انتقال |
| `ownership.transfer.approved` | تأیید درخواست |
| `ownership.transfer.rejected` | رد درخواست (با دلیل) |
| `ownership.transfer.cancelled` | لغو درخواست |
| `ownership.changed` | نهایی‌سازی و تغییر مالک |
| `jewelry.certificate.created` | ساخت شناسنامه |
| `jewelry.certificate.updated` | تأیید/رد/ویرایش شناسنامه |
| `jewelry.certificate.deleted` | حذف شناسنامه |
| `repair.status.updated` | تغییر وضعیت تعمیر |
| `security.access.denied` | تلاش دسترسی غیرمجاز |

هر رکورد شامل این اطلاعات است: کاربر، زمان، نشانی IP، مرورگر، آدرس
درخواست، متد HTTP، سطح اهمیت و مقادیر پیشین/پسین.

مشاهده: `/admin/audit-logs` (نیازمند مجوز `audit_logs.view`)

## گزارش مفقودی و سرقت

| مسیر | کاربرد |
|------|--------|
| `/jewelry/report-stolen` | فرم عمومی اعلام سرقت/مفقودی |
| `/my-jewelry` | بخش گزارش‌های فعال |

پس از ثبت گزارش:

1. تنها مالک ثبت‌شده قطعه می‌تواند گزارش بدهد (بررسی مالکیت در کنترلر).
2. برای هر قطعه تنها یک گزارش «باز» ثبت می‌شود؛ تلاش دوم پیام خطا می‌گیرد.
3. قطعه در فهرست «گزارش‌های مفقودی» پنل مدیریت نمایش داده می‌شود.
4. امکان پیوست فایل گزارش پلیس وجود دارد (با اعتبارسنجی نوع واقعی فایل).

## سلب مسئولیت حقوقی

> **مهم:** سوابق این نرم‌افزار «خودِ اثبات مالکیت» نیستند.
>
> ثبت رکورد در این سامانه نشان‌دهنده آن است که «کاربران سامانه، عملیاتی
